# new-api 分析：能力对照、架构借鉴与 AGPL 许可证约束

> 来源：GitHub 仓库 QuantumNous/new-api（zread 检索 + 公开资料，2026 年 8 月 9 日）
> 研究方式：主会话轻量调研，未克隆仓库；结论供技术方案选型使用
> 许可证：AGPL-3.0（已核对仓库 LICENSE 原文）

## 一句话结论

new-api 是功能上与 LLM-portal 重叠最多的开源项目（多协议入站、模型映射、密钥、用量），其「SQLite 默认 + go:embed 单二进制」也直接验证了我们的部署形态。**但 AGPL-3.0 的网络传染条款使二开路线在闭源商用前提下不可行**；其转换层代码同样不可拷入非 AGPL 代码库。定位：**架构范本，不是基座，不是代码来源。**

## 能力对照（与 LLM-portal 需求基线）

| 我们的需求 | new-api 现状 |
|-----------|-------------|
| US-01 OpenAI 入口 | 有，主入口 |
| US-02 Anthropic 原生入口 | 有，原生 `/v1/messages`，Claude Code 可直连 |
| US-03 模型映射 | 有（渠道 + 模型重定向） |
| US-04 主备容灾 | 有（渠道优先级/重试） |
| US-05 System Prompt 策略 | 弱（无按密钥/路由的注入/追加/替换策略引擎） |
| US-06 虚拟密钥/限额 | 有，且远超需求（多用户、分组、充值计费） |
| US-07 用量成本 | 有，面向计费结算设计 |
| US-08 Prompt Cache 治理 | 部分（透传为主，无自动注入策略与命中率治理面板） |
| US-09 内容优化管道 | 无，且其架构未为字节级稳定改写预留控制点 |

差异本质：new-api 面向「API 分销/计费」多租户场景；我们的差异化（US-05/08/09 的字节级序列化控制）恰好是它没有、也难以在其管线上嫁接的部分。

## 值得借鉴的架构设计

- **Adaptor 扇入模式**：每个上游 Adaptor 实现 `ConvertOpenAIRequest` / `ConvertClaudeRequest` / `ConvertGeminiRequest`，任意入站协议先归一再出站——与我们「任意入口 → 任意上游」的转换矩阵同构。
- **声明式转换器 ID**：如 `anthropic_messages_to_openai_chat_completions`，转换路径显式命名、可枚举可测试。
- **转换链审计**：`RelayInfo.RequestConversionChain` 记录请求经过的转换序列——正合我们 C4「修改可审计」约束，值得同款设计。
- **部署形态实证**：SQLite 默认存储 + go:embed 把前端嵌入单二进制，大量真实部署验证了「单文件/单容器 + SQLite」在网关场景成立，支撑我们的 US-10 与 SQLite 决策。

## AGPL-3.0 约束（决定性）

- 网络传染条款：修改后以网络服务形式提供，必须向使用者公开全部修改版源码。二开 = 整个产品被迫 AGPL 开源，对面向中小企业的商用自部署产品不可接受（除非主动选择全开源商业模式）。
- 拷贝其转换层/计量代码入自研代码库同样触发传染——**代码只可读作参考，不可搬运**。
- 结论：原「方案 C：new-api 二开」除非接受整体 AGPL，否则出局。

## 结论

1. 二开路线否决（许可证 + 多租户计费架构与 Non-Goals 冲突双重原因）。
2. 自研时按其验证过的三个设计走：Adaptor 扇入、命名转换器、转换链审计字段。
3. 把 new-api 列为兼容性对照物：我们的双入口行为可与其做黑盒对比测试（行为对齐，不看代码也能测）。
