# rtk 分析：agent 端 token 优化及其在网关上游侧的适用性

> 来源：GitHub 仓库 rtk-ai/rtk（浅克隆于 planning/01-raw/rtk，2026 年 8 月 9 日）
> 研究深度：README_zh、项目自述文档（CLAUDE.md/.claude/rules）、TOML 过滤器样例；未逐行审读源码
> 用途：LLM-portal「缓存管理 / 内容优化」需求决策输入

## 一、rtk 是什么

一句话：**Rust 编写的 CLI 代理，在命令输出进入 LLM 上下文之前过滤压缩，削减最多 90% 的 bash 输出 token**。

展开：编码 agent（Claude Code 等）执行 shell 命令时，原始输出（git status、测试日志、构建日志）冗余极高。rtk 通过 hook 把命令重写为 `rtk <cmd>`，由 rtk 执行真实命令并对输出做命令感知的压缩（如 `git log` 只留哈希/作者/标题；测试只显示失败项，通过项折叠为计数），再交给 agent。单二进制、无依赖、<10ms 开销、无 async，单线程设计。

## 二、核心机制

1. **四种压缩策略**：智能过滤（去噪音/样板）、分组（相似项聚合）、截断（保留相关上下文）、去重（重复日志行合并计数）。
2. **命令感知的专用过滤器**：按生态（git/cargo/npm/pytest/docker…）内置约 60+ 过滤模块，每个过滤器针对该命令的已知输出格式定制规则。
3. **TOML 声明式过滤 DSL**：`match_command`（正则匹配命令）、`strip_lines_matching`（正则删行）、`strip_ansi`、`max_lines`、`on_empty`（空结果占位文案），并支持内联测试用例（input/expected）。用户可在 `~/.config/rtk/filters/` 或项目 `.rtk/filters/` 自定义。
4. **兜底与逃生**：过滤失败即透传原始输出（fallback pattern，绝不阻塞用户）；`rtk proxy <cmd>` 完全跳过过滤仅记录指标；错误时保留原始输出可恢复（tee）。
5. **度量**：SQLite 记录每次命令的原始/过滤后字节数，`rtk gain` 展示节省统计。token 按 `字节/4` 估算——**百分比可靠，绝对值仅近似**。官方明确声明：削减 90% bash 输出 ≠ 账单降 90%（bash 输出只是输入 token 的一部分，输入 token 又只是账单的一部分）。

## 三、它在链路中的位置（关键）

rtk 是 **agent 端 CLI 包装器**，位于 agent 与 shell 之间。它能安全压缩的根本原因是：**它知道自己在执行什么命令**（命令语义 + 已知输出格式 → 针对性规则），且压缩发生在内容**进入对话历史之前**——后续所有轮次自然复用压缩后的版本，与 prompt cache 天然兼容。

## 四、迁移到 LLM 网关上游侧的评估

网关看到的是完整请求体（含历史消息、tool_result 块）。对编码 agent 流量，工具输出以结构化块存在，网关**技术上可以**识别并压缩。但与 rtk 的处境有本质差异：

| 维度 | rtk（agent 端） | 网关上游侧 |
|------|----------------|-----------|
| 命令语义 | 完整（自己执行命令） | 缺失（只见文本，需从 tool_result 内容猜测格式） |
| 压缩时机 | 入史前，一次性 | 每轮请求都要对同一历史重复变换 |
| prompt cache | 无影响 | **变换必须逐字节确定性**，否则前缀漂移、缓存全失效 |
| 出错恢复 | 透传 + tee 恢复 | 内容已转发，agent 拿到的历史被永久改写 |
| 正确性风险 | 低（规则针对已知格式） | 中高（误删 agent 需要的信息，且难以归因） |

**核心结论**：rtk 的「规则手法」可迁移（ANSI 剥离、删噪音行、去重、截断），但「压缩决策」不可同等迁移——网关缺少命令语义，只能做保守的、格式无关的变换。且必须满足硬约束：

- **确定性 + 版本化**：同一输入永远产出同一输出；规则集带版本号，版本变更等于主动宣告缓存失效。客户端每轮重发原始历史，网关重复施加同一变换，变换后前缀才能逐字节稳定，prompt cache 才能命中。
- **只动 tool_result / 工具输出类内容**，绝不动 system prompt、用户消息、assistant 消息、tool_use 参数。
- **只在请求侧**（请求体非流式），不碰流式响应。
- **按 key 可开关 + 全局逃生阀**，出问题可立即关闭（对应 rtk 的 proxy 模式）。

## 五、对 LLM-portal 的建议（按优先级）

1. **观测先行（MVP 必做，零风险）**：仪表盘统计每 key 的 token 构成——tool_result 占比、超大内容块 Top-N、重复度估计，量化「可优化空间」。相当于网关版 `rtk gain`/`rtk discover`。收益：直接支撑优化决策与客户沟通；代价：低（计量管道顺带实现）。
2. **保守内容优化管道（MVP 可选项，默认关闭，按 key 开启）**：仅对 tool_result 块做三种无语义变换——ANSI 剥离、连续重复行折叠（`×N` 标记）、超大块截断（保留头尾 + 明确截断标记）。收益：对编码 agent 流量可观（rtk 实测同类手法 60-90% 削减 bash 输出）；风险：中（截断可能删掉有用信息，需阈值保守）；代价：中（确定性/版本化机制是主要工程量）。
3. **变换与 prompt cache 的互锁设计（做 2 就必须做）**：变换函数纯化 + 规则版本入缓存键；文档明示「规则升级 = 缓存失效一次」。代价：设计约束而非独立功能。
4. **借鉴 TOML 过滤 DSL 形态（后续版本)**：把 2 的规则做成声明式配置（匹配条件 + 变换 + 内联测试），管理员可自定义。rtk 已验证这种形态对运维友好。
5. **不做**：LLM 二次摘要/语义压缩（成本、延迟、不确定性都高）；对非工具输出内容的任何改写。**更优路径**：建议客户在 agent 端直接装 rtk（Apache 2.0），网关只负责度量验证效果——两者互补而非竞争。

## 六、对「缓存管理」需求定义的直接启示

- 缓存管理应包含两层：**prompt cache 治理**（Anthropic cache_control 透传/自动注入、命中率与节省统计、协议转换时保留缓存语义）+ **可选的内容优化管道**（上述 2/3）。
- 精确响应缓存（相同请求直接回缓存结果）与 rtk 无关，是独立特性，按常规网关需求单独决策。
- 任何内容改写特性都必须与 prompt cache 特性联合设计，二者互锁是本产品区别于「无脑改写」竞品的技术护城河。
